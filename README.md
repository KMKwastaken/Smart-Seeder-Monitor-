# Smart Agricultural Seeder Monitoring System

An educational portfolio project aligned with the supplied Bourgault Software/Firmware Developer Intern handoff: C++ development, C# familiarity, Python test automation, Linux tooling, diagnostics, documentation, and software/hardware integration thinking.

**SIMULATED DATA ONLY. This is not real agricultural control software.** It has no hardware connection or actuator commands, is not affiliated with Bourgault, and uses invented thresholds rather than manufacturer specifications. No field testing or real-time guarantees are claimed.

## Try the dashboard immediately

Install Python 3.10+; no third-party packages are required to view the included replay. From the extracted project directory:

```sh
python dashboard/server.py
```

On Linux use `python3` if needed. Open http://127.0.0.1:8080 in your browser. Play/pause, restart, and scrub through 60 seconds of synthetic seeding. The metrics, flow chart, and active faults update together. Ctrl+C stops the server. The replay ends at the final sample; use Restart and Play to run it again.

## Build and test on Linux

Prerequisites: C++17 compiler, CMake 3.16+, Python 3.10+. On Ubuntu/Debian:

```sh
sudo apt-get update
sudo apt-get install -y build-essential cmake python3 python3-venv
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
./build/seeder_sim --scenario demo --ticks 60 > data/my-run.jsonl
python dashboard/server.py --data data/my-run.jsonl
```

The executable emits JSON Lines to stdout, errors to stderr, and returns 2 for invalid arguments. Each tick represents one simulated second; generation runs as fast as possible. The dashboard replays at one sample per second, independent of wall-clock acquisition.

## Windows

Install Python and Visual Studio Build Tools with Desktop development with C++, including CMake. In a developer PowerShell:

```powershell
cmake -S . -B build
cmake --build build --config Release
$env:SEEDER_SIM = "$PWD/build/Release/seeder_sim.exe"
python -m venv .venv
.venv/Scripts/Activate.ps1
python -m pip install -r requirements-dev.txt
python -m pytest -q
python dashboard/server.py
```

For a single-configuration generator the executable may be `build/seeder_sim.exe`; adjust `SEEDER_SIM`. To save telemetry in Windows PowerShell 5.1 use `build/Release/seeder_sim.exe --scenario demo | Set-Content -Encoding utf8 data/my-run.jsonl` (avoids UTF-16 redirection).

## Optional C# .NET monitor

Install the .NET 8 SDK (a runtime alone cannot compile). No NuGet dependencies:

```sh
dotnet build dotnet/SeederMonitor.csproj
dotnet run --project dotnet -- data/demo.jsonl
```

This prints each sample and a summary. The primary graphical interface is the portable browser dashboard; the C# component is a console replay monitor, not a native desktop GUI.

## Scenarios and expected behavior

`--scenario normal|blockage|low-tank|low-fan|sensor-loss|stopped|demo`, `--ticks 1..100000`. Default: 60 ticks of demo. `--help` lists arguments. `--probe speed flow tank rpm connected` injects a constant reading for boundary testing.

Demo: ticks 0–9 healthy; 10–19 zero flow (BLOCKAGE starts at 12 after three samples); 20–24 recovery; 25–34 low tank; 35–39 recovery; 40–44 low fan; 45–49 recovery; 50–54 disconnected sensor; 55–59 recovery. Faults represent active state, not latched alarms. Multiple faults may coexist. There is no acknowledgement or control action.

## Repository guide

- `simulator/main.cpp`: deterministic sensor model, detector, CLI and JSONL writer.
- `dashboard/`: local read-only replay server and responsive graphical dashboard.
- `dotnet/`: C# JSONL console monitor.
- `tests/`: pytest tests against the compiled C++ binary plus HTTP integration checks.
- `data/demo.jsonl`: output generated by the actual simulator.
- `docs/`: architecture, validation procedure, requirements mapping, delivery verification.
- `.github/workflows/ci.yml`: Linux build, pytest, C# build/replay, uploaded JUnit report.

## Fault history

The dashboard lists fault episodes with start time, cleared time (or Active), and elapsed duration in simulated seconds. History follows the time slider and resets on Restart; future events stay hidden. Repeated faults create separate entries. Cleared means absent from detector output, not a confirmed repair. History is reconstructed from the loaded replay and is not a persistent alarm database.

History tests require Node.js 18+ (development only): `node --test tests/history.test.cjs`. Node is not needed to run the dashboard.
